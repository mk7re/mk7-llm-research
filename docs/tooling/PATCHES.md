# Patch files

How research delivers template changes: edit a copy of `template/`, compile-check it, and turn the difference into a
`.patch` file. `template/` itself is never edited.

## Contents

- [Making a patch](#making-a-patch): the five steps, from the work copy to `git apply --check`
- [What the patch must be](#what-the-patch-must-be): what it may touch, where it applies, checking evidence against it,
  updating it when the repository has moved on
- [Writing the template changes](#writing-the-template-changes): final names, comments for programmers, enums for
  members that hold states or kinds

## Making a patch

Research that needs no template change uses `<repo>/include` as generated by `make`, and touches nothing. As soon as a
template has to change, work on a copy, from the repository root:

1. Copy the templates twice into a work folder:

   ```
   W=mk7-llm-research/local/work/<topic>
   mkdir -p $W/a $W/b
   cp -r template $W/a/template     # untouched, the base of the patch
   cp -r template $W/b/template     # the copy that gets edited
   ```

2. Edit only `$W/b/template`.
3. Generate and compile-check the headers of the copy. `--templates` points every template command at the copy; its
   headers go to `$W/b/include`:

   ```
   mk7-llm-research/mk7 --templates $W/b/template verify --version EUR_REV2
   mk7-llm-research/mk7 --templates $W/b/template verify      # USA_REV1, what CI compiles
   mk7-llm-research/mk7 --templates $W/b/template struct <Class>
   ```

   Setting `MK7_TEMPLATES=$W/b/template` does the same for a whole shell session.
4. Produce the patch:

   ```
   (cd $W && LC_ALL=C diff -ruN a/template b/template) > mk7-llm-research/pending-verification/<topic>/<name>.patch
   ```

5. Check that it applies to the repository, without applying it:

   ```
   git apply --check mk7-llm-research/pending-verification/<topic>/<name>.patch
   ```

## What the patch must be

The patch is the deliverable. It changes files under `template/` only and applies with `git apply` from the repository
root, on the base commit written in the topic `README.md`. The work folder is disposable.

`--templates` also applies to the commands that map binary evidence onto the templates (`access`, `decomp --as`), so
evidence can be checked against the edited layout.

### When the base commit has moved on

A patch that no longer applies because `template/` changed after its base commit is not a failure of the research or of
a review pass. The agent that finds it, in any pass, updates the patch to the latest commit and carries on:

1. Make a fresh work copy of the current `template/` ([Making a patch](#making-a-patch)) and apply the patch to its
   `b/` copy (`patch -p1` from `$W/b`). Hunks that are rejected are made by hand, keeping the changes of the newer
   commits.
2. Run `verify` on the copy, regenerate the patch, and check it with `git apply --check`.
3. Set `Base commit` in the topic `README.md` to the new commit, and note the update in the pass's review.

If a newer commit already names or describes something the patch changes (the same member under another name, a moved
offset, a new size), the topic is brought in line with the repository where both mean the same thing; where they
disagree, the difference is checked against `eur2` like any other claim, and written in the review.

## Writing the template changes

The templates are read by programmers who use the generated headers, not by readers of the research. A patch writes into
them what such a programmer needs to use a class. The evidence, and which functions set, read or test a member, stay in
the topic document ([Glossary and naming](WRITING.md#glossary-and-naming)).

### Names

Every member, function and enum the patch adds or renames gets its final name, chosen as described in [Glossary and
naming](WRITING.md#glossary-and-naming). Names and comments use no provisional wording ("provisional", "probably",
"meaning unknown"): what is not understood is written in the topic document, under `## Open questions`.

### Comments

- A member's comment goes after the member, on the same line:

  ```
  /M/u8 m_next_num/0x1/0x4/ // number of valid entries in m_next_infos
  ```

- It is written for someone using the class: what the member holds, its unit, its range, the meaning of special values,
  how it relates to other members. It is kept concise; details beyond that go into the topic document.
- Only when even a concise comment does not fit in one line, it goes on the lines before the member instead, as several
  `//` lines:

  ```
  // Return code ID with which the source child ends. When m_src_subsection_index is -1 (the source
  // is the sequence itself), enter code ID with which the sequence starts
  /M/u16 m_src_code/0x2/0x02/
  ```
- It does not say where the member is set, read, cleared or tested (`set by FieldDirector::createBeforeStructure`,
  `cleared every frame by LapRankChecker::calc`), and it cites no finding or evidence.
- A member whose name and type already say what it is has no comment.
- A class or struct may have a one-line comment on the line before it, saying what it is.

### Enums

A member that holds one of a set of values (a state, a kind, a mode, a type) is typed with an enum instead of an
integer type.

- If `template/` already has an enum for those values, the member uses it.
- Otherwise the patch declares an `enum class E<Name> : <base type>` at the top of the `public:` section of the class the
  member belongs to, as `Demo::DemoCameraDirector::EState` is. The base type is the integer type the member had, so the
  layout does not change.
- The name comes from the symbols or the game when they give one (a symbol, the names of the state functions, a
  string); otherwise the research invents one that says what the values are. Either way the enum is listed in the topic
  glossary.
- Only the values known from the research are listed, each with its number written out (`IDLE = 0`), since values in
  between may be missing. The other values do not have to be researched, and no placeholders are added for them.
- Values are named in `UPPER_SNAKE_CASE`, and a value's comment follows the same rule as a member's: after the value, or on the lines
  before it when a concise comment does not fit in one line.

```
    /START_CLASS/NAME@AIAutoSteer/SIZE@0x100/VTABLE@True/
    public:
        enum class EState : u32 {
            IDLE = 0,
            AVOID = 1,
            WAIT = 6,       // stopped before a train crossing
        };
        ...
        /M/EState m_state/0x4/0x.../
```
